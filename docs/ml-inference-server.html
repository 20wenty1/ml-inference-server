Architecture

Every request takes this exact path

No ORM, no framework routing, no managed queue. Six real steps, each one code you can read.

01 · client
Browser
Sends a raw POST with the message text as the body.
02 · c-server
accept() + thread
A new pthread is spawned per connection. Nothing blocks the accept loop.
03 · c-server
Rate limiter
IP checked against a rolling 10s window before anything else runs.
04 · worker pool
Round-robin pick
Mutex-protected index selects 1 of 3 persistent workers.
w1w2w3
05 · pytorch
Forward pass
TF-IDF (bigrams) → linear → ReLU → dropout → linear → sigmoid.
06 · response
JSON back to client
Prediction travels back through the same C server, same thread.

A real bug surfaced along the way

The original parser assumed one read() call always returned the full HTTP request. Under real concurrent load, TCP delivered some requests in multiple chunks — causing false "empty body" errors. Fixed with a read loop that keeps going until Content-Length is actually satisfied.

Hardening

What's actually protected

Real, explainable fixes — not a checklist for show.

ACTIVE
Client connection timeout
If someone connects but sends data extremely slowly (or never finishes), the server drops them after a few seconds instead of getting stuck waiting.
SO_RCVTIMEO · 5s
ACTIVE
Oversized request rejection
If a request claims to be bigger than the server can safely handle, it's rejected outright instead of silently cutting off part of the message.
413 Payload Too Large
ACTIVE
IP-based rate limiting
Keeps track of how many requests each visitor sends, and slows down anyone sending way too many, too fast.
20 req / 10s
ACTIVE
Worker connection timeout
If the AI model gets stuck instead of failing cleanly, the server notices and moves on rather than freezing up too.
